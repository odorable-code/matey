기획서 기준 DB/구현 분리 정리 (최종) - 2026-04-24
목적: 중복 없이, 실제 작업 기준으로 정리

==================================================
1) DB에서 수정/보완해야 하는 것 (스키마)
==================================================

[A. 공통 문법/타입]
- 잘못된 기본값 문법 수정
  - DEFAULT DEFAULT ...
  - DEFAULT UNIQUE
  - DEFAULT AUTO_INCREMENT PRIMARY KEY
  - CURRENT_TIMESTAMP,, (콤마 중복)
  - DEFAULT EARN / USE / ADJUST (문자열 기본값 문법)
- FK 컬럼 타입 통일 (PK와 동일 타입, BIGINT 권장)

[B. 제약/인덱스]
- USER.email UNIQUE
- ROLE.role_code UNIQUE
- SOCIAL_LOGIN(provider, provider_user_id) UNIQUE
- AUTO_LOGIN.token_hash UNIQUE
- PASSWORD_RESET_TOKEN.token_hash UNIQUE
- USER_NOTIFICATION_SETTING (user_id, notification_type_id) UNIQUE
- USER_ROLE (user_id, role_id) UNIQUE 또는 복합 PK
- USER_ACTIVITY_DAILY (user_id, activity_date) UNIQUE
- MESSAGE_ANALYSIS.message_id UNIQUE (1 메시지 1 분석)
- 반응 중복 방지 UNIQUE
  - (user_id, post_id, reaction_type)
  - (user_id, comment_id, reaction_type)

[C. 도메인 구조]
- USER 역할 모델 통일
  - USER.role_id 단일 구조 또는 USER_ROLE 다대다 중 하나 선택
- SUPPORT 보완
  - type(INQUIRY/REPORT/SUGGEST) 컬럼 추가
  - 신고 기능 유지 시 target_type, target_id 컬럼 추가
  - updated_at 컬럼 추가
- SUPPORT_REASON 보완
  - request_type 오타 수정: REFORT -> REPORT
  - reason_name NOT NULL 검토
- USER_NOTIFICATION_SETTING 보완
  - notification_type_id를 BIGINT로 통일
- 감사/운영 테이블 추가 권장
  - LOGIN_HISTORY (login_history_id, user_id, ip_address, user_agent, success_yn, fail_reason, created_at)
  - SECURITY_EVENT_LOG (event_id, user_id, event_type, ip_address, detail, created_at)
  - ADMIN_ACTIVITY_LOG (activity_id, admin_user_id, action_type, target_type, target_id, created_at)
- 삭제/정지 운영을 위한 컬럼 보강 권장
  - USER.deleted_at, USER.banned_at, USER.failed_login_count, USER.last_failed_login_at
  - SUPPORT_ANSWER.updated_at
  - ADMIN_NOTICE.updated_at (공지 수정 이력 추적)
- 개인정보/운영 기준 컬럼 보강 권장
  - USER.email_verified_at (이메일 검증 상태 추적)
  - PASSWORD_RESET_TOKEN.used_ip (선택)
  - AUTO_LOGIN.revoked_at, revoke_reason (선택)

[D. 토큰 관련 - DB에서 반드시 손볼 것]
- AUTO_LOGIN
  - token_hash UNIQUE 추가
  - expired_at 인덱스 추가
  - (선택) device_info 유지 또는 requested_ip/user_agent로 분리
- PASSWORD_RESET_TOKEN
  - last_used_at -> used_at 컬럼명 변경 권장
  - device_info -> requested_ip (또는 requested_ip + requested_user_agent) 권장
  - token_hash UNIQUE 추가
  - expires_at 인덱스 추가

[E. 반응 테이블]
- POST/COMMENT 반응(좋아요/싫어요/신고) 기능은 이번 범위에서 제외(미구현)한다.
- 따라서 운영 로직/집계는 POST/COMMENT의 `like_count`, `dislike_count`, `report_count` 등을 갱신하지 않는 전제다.

==================================================
2) 코딩으로 구현할 수 있는 것 (서비스/API/배치)
==================================================

[A. 인증/권한 로직]
- USER.status 기반 로그인 차단 (ACTIVE만 로그인 허용)
- 관리자 권한 체크 (ADMIN만 관리자 기능 접근)
- SUPPORT_ANSWER 작성 권한 제한
- 이메일 인증 상태(email_verified_at) 검사 후 주요 기능 제한(선택)
- 로그인 실패 횟수 기반 임시 잠금 정책(예: 5회 실패 시 15분 잠금)

[B. 토큰 처리 로직]
- Access Token: DB 저장 없이 서명/만료 기반 검증
- AUTO_LOGIN: 원문 토큰 저장/비교 금지, hash 비교만
- PASSWORD_RESET_TOKEN:
  - 만료(expires_at) + 미사용(used_at IS NULL) 동시 검증
  - 재설정 성공 시 used_at 즉시 업데이트
  - 새 요청 시 기존 미사용 토큰 무효화(정책 선택)
- Refresh/자동로그인 토큰 로테이션 정책(재발급 시 이전 토큰 무효화)
- 로그아웃 시 해당 AUTO_LOGIN 토큰 revoke 처리(컬럼 사용 시 revoked_at 업데이트)

[C. 운영/보안 배치]
- 만료 AUTO_LOGIN 정리 배치
- 만료/사용완료 PASSWORD_RESET_TOKEN 정리 배치
- 로그인 실패 누적 초기화 배치(정책 적용 시)
- LOGIN_HISTORY/SECURITY_EVENT_LOG 보관기간 기준 삭제 배치
- 공지/FAQ/지원 데이터 백업 스냅샷 정책(일 단위) 수립
- 장애 대응을 위한 DB 백업 복구 리허설(월 1회) 계획 포함

[D. 문의/신고 검증 로직]
- SUPPORT.type별 필수값 검증
- REPORT일 때만 target_type/target_id 요구
- 비활성 reason, 빈 내용, 비정상 조합 차단
- 신고 과다 요청(rate limit) 제한
- 신고/문의 내용 길이 제한 및 금칙어/악성 패턴 필터링

[F. 반응 도메인 구현 로직]
- target_type 기반 대상 존재 검증
  - POST면 POST 존재 확인
  - COMMENT면 COMMENT 존재 확인
- reaction_type 유효성 검증
  - POST: LIKE / DISLIKE / REPORT
  - COMMENT: LIKE / REPORT (정책에 맞게 제한)
- 중복 반응 처리 정책 통일
  - 동일 반응 재요청 시 무시 또는 토글 처리
  - 서로 배타 반응(예: LIKE vs DISLIKE) 전환 규칙 정의
- 집계 갱신 전략 통일
  - 실시간 카운트 반영 또는 배치 집계 중 한 가지 선택

[G. 운영 관측성(필수)]
- 모든 인증 실패/비번 재설정 요청/권한 거부 이벤트를 서버 로그에 구조화(JSON) 기록
- 관리자 기능 변경(FAQ/공지/지원답변)은 누가/언제/무엇을 변경했는지 로그 기록
- 보안 알림 기준 정의
  - 새 IP 로그인
  - 짧은 시간 내 다수 실패 로그인
  - 비밀번호 재설정 다량 요청

==================================================
3) 토큰 관련 최종 결론
==================================================

- "DB에서 토큰 관련 수정이 없는가?" -> 아니오, 수정 필요함.
- 수정 핵심은 두 가지:
  1) AUTO_LOGIN / PASSWORD_RESET_TOKEN에 UNIQUE + 인덱스 보강
  2) PASSWORD_RESET_TOKEN 컬럼 의미 정리(used_at, requested_ip 등)
- 분리 원칙:
  - AUTO_LOGIN(로그인 유지)과 PASSWORD_RESET_TOKEN(비번 재설정)은 목적이 달라 분리 유지

==================================================
4) 최근 파일 점검 반영 (기준 문서 업데이트)
==================================================

점검 범위:
- DB_기획서_기준_정리.txt, 요청 정리 문서를 제외한 파일 기준 확인
- 핵심 반영 대상: DB 초안.sql

[A. DB 초안에서 확인된 "이미 반영된 것"]
- 상담/분석 도메인 테이블 존재
  - MESSAGE
  - CHAT_ROOM
  - MESSAGE_ANALYSIS
  - SATISFACTION
  - COUNSEL_FEEDBACK
- 감정 분석 관련 신규 테이블 존재
  - EMOTION_CATEGORY
  - MESSAGE_EMOTION_SCORE
  - MESSAGE_CONTENT_SECURE
- MESSAGE_ANALYSIS에 dominant_emotion_id 추가됨
- 중복 키 정리 반영
  - MESSAGE.user_id 제거
  - SATISFACTION.user_id 제거
  - MESSAGE_ANALYSIS.bot_id 제거

[B. DB 초안에서 확인된 "아직 수정 필요한 것"]
- 공통 문법 오류 일부 잔존
  - 제약/유니크를 COMMENT로만 남긴 구간을 실제 제약으로 반영 필요
  - ENUM 성격 값은 CHECK/코드테이블 기준으로 정식 제약화 필요
- 타입/의미 불일치
  - MESSAGE_CONTENT_SECURE.emotion_score 타입/의미 재정의 필요(DECIMAL 정밀도 명확화 권장)
- 알림 타입 FK 컬럼 점검
  - NOTIFICATION.notification_type_id 타입은 BIGINT로 맞춰짐
  - USER_NOTIFICATION_SETTING.notification_type_id 타입은 BIGINT로 맞춰짐
- 피드백 도메인 명칭 확정
  - MESSAGE_FEEDBACK 미사용
  - COUNSEL_FEEDBACK 단일 명칭으로 유지

[C. 상담 메시지 도메인 최종 기준 (이 문서 기준으로 확정)]
- 키 기준 경로를 단일화:
  - CHAT_ROOM: user_id, bot_id
  - MESSAGE: message_id, chat_room_id, sender_type, created_at (user_id 중복 저장 지양)
  - MESSAGE_ANALYSIS: analysis_id, message_id(UNIQUE), dominant_emotion_id, risk_level, is_high_risk, analyzed_at
  - MESSAGE_EMOTION_SCORE: (analysis_id, emotion_id) UNIQUE + emotion_score(0~1)
- 세션 평가 vs 메시지 반응 분리:
  - 세션 평가: chat_room_id 기준 (점수/사유 분리)
  - 메시지 반응: `COUNSEL_FEEDBACK`(message_id 기준) 단일 유지
- 중복 컬럼 최소화 원칙:
  - 하위 테이블에서 user_id/bot_id를 반복 저장하지 않고, 상위 FK 조인으로 조회

[D. 즉시 적용 우선순위 (DB 초안 수정 순서)]
1) COMMENT 기반 제약을 실제 UNIQUE/FK/INDEX로 반영
2) 감정 분석 3종 테이블 재정의
   - EMOTION_CATEGORY
   - MESSAGE_ANALYSIS
   - MESSAGE_EMOTION_SCORE
3) MESSAGE_CONTENT_SECURE 컬럼 의미/타입 정리
4) 평가 도메인(세션/메시지) 제약 확정

[E. 운영 관점 결론]
- 현재 DB 초안은 "기능 항목"은 상당 부분 들어왔지만,
  스키마 정합성과 제약 설계가 아직 기획서 기준에 완전히 맞지 않다.
- 다음 단계는 신규 테이블 추가보다 "제약 확정 + 타입/의미 정리"가 우선이다.
